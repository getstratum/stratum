# GCP failure test, 2026-10-14

First run of the reference deployment in `deploy/gcp` on a real Google Cloud
project, with every failure scenario of the test plan. The goal was to
check the high-availability claims of the open-source edition (ADR-0006)
under load, through the same edge a customer would use.

**Result: Stratum produced 0 errors in 69,605 requests.** The 31 failed
requests came from Google's load balancer (28) and from the network path
between the load generator and the load balancer (3). One design gap
showed up: a gateway pod replaced during a control plane outage could not
start. ADR-0008 closes it.

## Environment

| Piece | Configuration |
|---|---|
| Region | `us-central1`, one dedicated project, deleted after the run |
| Gateways | GKE Autopilot, regional (3 zones), 3 replicas (HPA 3–12), Helm chart `deploy/helm/stratum-gateway` with `deploy/gcp/helm/values-gcp.yaml` |
| Control plane | 2 replicas on the same cluster, Cloud SQL Auth Proxy as a native sidecar |
| Database | Cloud SQL for PostgreSQL 16, regional HA, PITR |
| Shared quota store | Memorystore for Valkey, 1 replica, AOF, private access only |
| Edge | Global external Application Load Balancer through the Gateway API, Google-managed certificate, Cloud Armor |
| Egress | Cloud NAT with a fixed IP (the only address allowed on the sync endpoint) |
| Provider | Mock OpenAI-compatible LLM in the cluster, with a fixed response delay |
| Load | k6 inside the cluster calling the **public hostname**, so DNS, TLS, the load balancer, Cloud Armor and Cloud NAT are part of every request; 70% unary, 30% streamed |

Latency is not a result of this run: p50 was about 311 ms and p95 about
2.2–2.25 s in every scenario, which is the mock provider's configured delay.

"Errors on the path" are failures that never reached a gateway or were
produced by the load balancer itself. The harness used for this run counted
them together with gateway errors; each one was attributed by hand from the
load balancer's request logs (`statusDetails`), the gateway logs and the k6
logs, as described below. The harness now does this attribution itself
(see "What changed after this run").

### Evidence per scenario

**Rolling restart #1.** 27 responses with status 500, 66 bytes, about
2.7 ms, and no `statusDetails` in the load balancer log: answered by the
load balancer without contacting a backend. The gateways logged only 200s
in that window. The gateway pods drained correctly (readiness fails, 45 s
delay, in-flight streams finish). This is above the 0.1% the harness now
tolerates on the path, so the next run repeats this scenario to see whether
it reproduces.

**Zone loss.** One `read: connection reset by peer` in k6, on the
k6 → Cloud NAT → load balancer hop. The load balancer has no log entry for
it.

**Rolling restart #2.** One `503 retriable_error` from the load balancer
(18:25:56Z, 0.2 s): a transient Google front-end error that the load
balancer marks as retriable.

**Valkey outage.** Valkey blocked at 20:40:20 and restored at 20:41:54.
During the cut, quota flushes failed 14 times and 175,400 tokens were
counted locally; 10 s after the restore, 0 tokens were pending. No request
failed: Valkey is not on the request path (ADR-0004).

**Control plane outage.** Control plane scaled to 0 at 20:45:54. The
gateways kept serving with the snapshot in memory; the largest snapshot age
reached 322 s. The only load balancer errors were 503s on
`/api/internal/sync` (`failed_to_pick_backend`, then
`failed_to_connect_to_backend`), which is the expected answer with no
control plane pods. The two failed requests were TCP resets in k6 at
20:49:17 and 20:49:21, on the same path as in the zone test; the gateways
logged no 5xx. The gateway pod deleted during the outage came back without
a snapshot and stayed unready: 2 of 3 gateways were ready until the control
plane returned.

**Database failover.** Started at 20:55:55, completed in 35 s. No gateway
request failed (the database is not on the gateway's path), and the control
plane's sync endpoint answered 200 afterwards without intervention.

## Findings and what changed after this run

| Finding | Change |
|---|---|
| A gateway pod that starts while the control plane is unreachable has no configuration and stays unready. On Kubernetes pods are replaced without anyone choosing to, so a long outage drains the data plane. | ADR-0008: gateways keep their encrypted snapshot in Valkey, next to them, and a new pod starts from it. The `cp-outage` scenario now requires the replacement pod to become ready during the outage. |
| The harness counted load balancer and network failures as Stratum failures. | k6 attributes each failure through the `X-Stratum-Request-Id` header the gateway sets on every response; the verdict counts only Stratum's, path failures are reported and flagged above 0.1%, and the load balancer's log is printed grouped by `statusDetails`. |
| Kit problems on a fresh project: Cloud Shell's `terraform` is a placeholder, PromQL alerts cannot be created before the metric exists, Autopilot caps the termination grace period at 600 s, a shell pipeline in the zone test. | Fixed in the kit: Terraform check, `metric_alerts` switch, `shutdownTimeoutSeconds` 520. |
| End-to-end availability depends on the path, not only on Stratum: 31 path failures in 69,605 requests is about 0.045%. | Documented: 99.99% end to end needs clients that retry connection errors and 5xx before the first byte, as the official OpenAI SDKs do by default. |

A review during the follow-up work also found that some revocations (a
removed key, a deactivated user, a team moved to another policy) reached
gateways only at the next full resync. That is fixed in the control plane's
sync endpoint; it was not exercised by this run.

## Not covered

- A real zone outage: Autopilot does not allow cordoning Google's nodes, so
  the zone scenario deletes the pods instead.
- A regional outage: out of scope for a single-region topology.
- Valkey losing its data (restart without persistence). The outage test cut
  the network; the counter-regression path is covered by unit tests only.
- ADR-0008 on GCP. It was implemented after this run; the next run
  validates it with the new `cp-outage` criterion.
