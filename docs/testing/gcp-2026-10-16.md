# GCP failure test, 2026-10-16

Second run of the reference deployment in `deploy/gcp`, on a new project,
with images built from commit `40c5efd` (`main` with the console access
control, console connections, audit log and request log partitions). It was
the first run with the gateways' shared snapshot in Valkey (ADR-0008) and
with the console's functional test.

**Result: Stratum produced 0 errors in 50,400 requests under load.** The
80 failed requests were answered by Google's load balancer (79) or lost on
the network path (1). The new criterion of ADR-0008 held: a gateway pod
created while the control plane was down started from the snapshot in
Valkey 10 s later and served. The console's functional test passed all 14
steps through the real deployment.

Three scenarios were marked FAIL. One is a real, reproduced load balancer
behaviour; the other two were false failures of the test harness. Both are
explained below, with what changed.

## Environment

Same topology as the [first run](gcp-2026-10-14.md): GKE Autopilot in
`us-central1` (3 zones), 3 gateway replicas, 2 control plane replicas,
Cloud SQL for PostgreSQL 16 regional HA, Memorystore for Valkey with one
replica, global external Application Load Balancer through the Gateway API
with Cloud Armor, Cloud NAT, a mock OpenAI-compatible provider, and k6
inside the cluster calling the public hostname (70% unary, 30% streamed).

p50 was about 311 ms and p95 about 2.2–2.36 s in every scenario: the mock
provider's configured delay, not a result.

### Evidence per scenario

**Console.** Sign-in, roles, providers, gateways, people, password change,
deactivation, audit log and sign-out, against the deployed console. An agent
key created in the console was accepted by the gateways through the public
load balancer 12.7 s after creation and refused 11.8 s after revocation,
inside the 30 s sync interval.

**Rolling restart.** 79 responses with status 500, 66 bytes, about 3 ms,
no `statusDetails` and no `X-Stratum-Request-Id`: answered by the load
balancer without reaching a gateway. The gateways logged no warning in that
window. They were spread evenly from 16:00:07 to 16:05:52 (about 0.5% of
requests), not grouped around pods starting or stopping, and stopped before
the rollout ended. Same signature as the 27 of the first run.

**Valkey outage.** Blocked at 16:17:32, restored at 16:22:05. No request
failed. Reading each gateway's metrics afterwards showed 40 quota flush
failures on each of the two pods that lived through the cut, 1 failed write
of the shared snapshot on each, and 0 pending tokens: the outage happened,
was detected and was reconciled. The harness printed "+0 flush failures"
and failed the detection check; see findings.

**Control plane outage.** Control plane scaled to 0 at 16:24:28; a gateway
pod deleted about a minute later. The replacement pod logged:

```text
16:25:31.76  no snapshot on disk yet; waiting for the first sync
16:25:31.99  sync with control plane failed (503 ...)          x4, with backoff
16:25:41.77  control plane did not answer in time; serving the snapshot
             shared through Valkey  version=21 waited=10s
```

All 3 gateways were ready during the outage and its
`stratum_snapshot_shared_bootstraps_total` was 1. The harness read 0 and
failed the check. The one path failure was a network error with no load
balancer log entry.

**Database failover.** Completed in 35 s. No gateway request failed and the
control plane's sync endpoint answered afterwards.

## Findings and what changed after this run

| Finding | Change |
|---|---|
| **A new load balancer answers some requests with 500 for minutes after it first serves.** Right after `make deploy` every request got 500 for about two minutes; then a residual ~0.5% until about 15 minutes after the deploy. Both runs saw it only in the first load after the deploy (27 errors on 2026-10-14, 79 now); the later loads had 0–1. The rollout is where it showed, not its cause: the zone scenario, which also replaces a pod, had none. This is a hypothesis that fits both runs; it was not confirmed with a second rollout before the environment was deleted. | `make deploy` waits for 30 consecutive 200s on `/readyz` through the load balancer before "Done". `make test` starts with a `warmup` scenario: 2-minute rounds of load until one has no path errors, each recorded, so the scenarios after it measure Stratum and the next run measures how long the edge takes to settle. If the rollout still shows these errors after a clean warm-up, the hypothesis is wrong and the next suspect is HTTP/1.1 keep-alive between the load balancer and pods that are shutting down. |
| **The harness turned unreadable metrics into 0.** It reads each gateway's `/metrics` through a port-forward from the operator's shell; during the run those reads failed (they took about 30 s per pod, and Cloud Shell's network had failed earlier that day), and a failed read counted as 0. That produced the two false failures, and it stretched the Valkey cut from 90 s to 4.5 min. | `metric()` uses a new port for every read, retries, skips pods being deleted, and returns an error instead of a number when a pod cannot be read; the scenarios then say "could not measure" instead of reporting a result. The Valkey cut no longer waits for the metric reads. |
| Failures the gateway never saw could not be examined afterwards: the k6 jobs were gone and their log had no response body. | Each k6 log is saved next to the results file, and `K6_FAILURE` lines include the `Server` and `Via` headers and the first 200 bytes of the body. |
| Kit friction on a new project: Terraform calls failed on Cloud Shell's network (connection refused, then "cannot assign requested address"); a `terraform.tfvars` kept from the previous run had `metric_alerts = true`, and Cloud Monitoring refuses an alert on a metric the project has never received (`stratum_snapshot_shared_write_failures_total` is new). | Documented in the troubleshooting table: re-run `make up` (with `TF_CLI_ARGS_apply=-parallelism=3` if the network keeps failing), and keep `metric_alerts = false` until after the first deploy. |

## Not covered

- Whether the load balancer's 500s disappear after warm-up: the next run
  answers it.
- A real zone outage and a regional outage, as in the first run.
- Valkey losing its data.
