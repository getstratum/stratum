# GCP failure test, 2026-10-18

Third run of the reference deployment in `deploy/gcp`, the release gate for
0.1.0. Images were built from `main` at `008c1f5`: the console redesign
(#39), installations that start empty (#42), base images pinned by digest
(#43) and, for the first time in GCP, **Valkey over TLS with token
authentication** (#44, ADR-0011).

**Result: Stratum produced 0 errors in 52,805 requests under load**, across
rolling restart, zone loss, Valkey outage, control plane outage and database
failover. 4 requests failed on the path (load balancer and network), within
every scenario's tolerance: 99.992% end to end. Every scenario passed, the
console's functional test passed its 18 steps, and the load balancer
hypothesis left open by the [previous run](gcp-2026-10-16.md) is confirmed.

## Environment

Same topology as the [first run](gcp-2026-10-14.md): GKE Autopilot in
`us-central1` (3 zones), 3 gateway replicas, 2 control plane replicas,
Cloud SQL for PostgreSQL 16 regional HA, Memorystore for Valkey with one
replica, global external Application Load Balancer through the Gateway API
with Cloud Armor, Cloud NAT, a mock OpenAI-compatible provider, and k6
inside the cluster calling the public hostname (70% unary, 30% streamed).

New in this run: Memorystore with `transit_encryption_mode =
SERVER_AUTHENTICATION` (a CA of the instance's own) and `authorization_mode
= TOKEN_AUTH`. The gateways connect with `rediss://` to the instance's IP,
trusting only that CA, and authenticate with the default user's token.

p50 was 311 ms and p95 about 2.24 s in every scenario: the mock provider's
configured delay (300 ms to the first byte, 20 chunks 100 ms apart when
streamed), not a result.

### Evidence per scenario

**Warm-up and rolling restart.** The load balancer had been serving for
over an hour; the first 2-minute round had no path errors, and the rolling
restart that followed had none either: 19,201 of 19,201. On 2026-10-14 and
2026-10-16 the rollout was the first load after the deploy and showed 27 and
79 load balancer errors. See findings.

**Shared quota with TLS.** `make test-quota-reset` deleted the month's
counters with `valkey-cli --tls` and the token, from a pod inside the
cluster; then Marketing's 30-request limit let 31 through across 3 replicas
(the counters are shared asynchronously, every second). 0 pending tokens
and 0 flush failures afterwards.

**Zone loss.** Both gateway pods in `us-central1-b` deleted under 40 req/s.
2 network errors on the path, no load balancer log entry for them, none
from the gateways.

**Valkey outage.** Blocked at 18:04:30, restored at 18:06:09 (99 s). No
request failed. During the cut the gateways recorded 37 more flush failures
and held 188,100 tokens pending; after it, 0 pending: counted, detected and
reconciled, now over TLS.

**Control plane outage.** Control plane scaled to 0 at 18:09:10, a gateway
pod deleted during the outage. All 3 gateways stayed ready; the replacement
started from the snapshot copy in Valkey (ADR-0008), read over TLS with the
token (ADR-0011). One request got `503
backend_connection_closed_before_data_sent_to_client` from the load
balancer: a connection to the pod the test deletes. The gateway keeps idle
connections 620 s, more than the 600 s Google recommends for this load
balancer's backends, so this is not a keep-alive mismatch.

**Database failover.** Started 18:15:12, finished in 55 s (35 s on
2026-10-16). One network error on the path; no gateway request failed and
the control plane's sync endpoint answered afterwards.

**Console.** All 18 steps against the deployed console, now with the
redesigned pages and the model catalog. An agent key created in the console
was accepted through the public load balancer 20.9 s after creation, its
usage appeared in the control plane 8.6 s after the request, and the key
was refused 9.6 s after revocation, all inside the 30 s sync interval.

## Findings

| Finding | What it means |
|---|---|
| **The load balancer's 500s belong to a newly created load balancer, not to rollouts.** A first run started right after the deploy (16:34) saw path errors in every warm-up round for 17 minutes (54, 65, 69, 31, 34, then 1 of 2,401 per round) and never got a clean round within the 6 allowed. The run at 17:45, on the same load balancer an hour later, was clean in round 1, and the rolling restart after it had 0 errors. | The hypothesis from 2026-10-16 holds. A new global load balancer needs more than 15 minutes to settle; after that, rolling restarts are clean. The warm-up is the right gate, and a fresh environment should wait about 20 minutes, or run the warm-up until it passes, before measuring anything. |
| **Valkey over TLS with token authentication works on Memorystore as designed.** The gateway verified the server certificate against the instance's CA by IP address; Terraform created the instance with the `google-beta` provider; `make deploy` read the token from the Memorystore API. | ADR-0011 is confirmed in GCP, with no cost in the scenarios that depend on Valkey (quota, Valkey outage, control plane outage). |
| A dropped Cloud Shell connection ends the run. The 16:34 run stopped during the rollout ("no k6 result"): the operator's shell lost the cluster while k6 kept running. | Run `make test` with its output in a file (`make test 2>&1 \| tee ~/test.log`). Cloud Shell keeps each terminal in tmux, so a reconnect returns to the run while the VM is alive. |

## Not covered

- A real zone outage and a regional outage, as in the first run.
- Valkey losing its data, and a Memorystore CA or token rotation.
- Long streams (minutes) during a rolling restart: the mock's streams last
  about 2 s.
